# 契約情報入力フォーム 仕様書

別のウェブアプリで再実装するための仕様書。フレームワーク非依存で書いてある。
参考として実装ファイル名を括弧書きで添えているが、読むのに前提ではない。

対象は「お客様情報アプリ（@pocket）の1レコードを検索して開き、編集して保存する」画面。
新規レコードを作る入口はこのフォームには無く、レコードは工事側の連携で作られる。

---

## 0. 全体の流れ

```
1. 利用者がお客様名で検索する            → 候補（レコードID + 表示名）
2. レコードIDを指定して1件開く            → 列定義 + 現在値
3. 画面が値を編集する（表示条件が随時変わる）
4. 保存する                              → payload を組み立てて1レコードを更新
```

画面は @pocket の**列番号を知らない**。列は「見出し（caption）の完全一致」で
実行時に解決する。したがって同じフォーム定義のまま、列の並び替えや
識別子の変更に追従できる（第5章）。

---

## 1. 入力項目の一覧

### 表の読み方

| 列 | 意味 |
|---|---|
| key | アプリ内部のキー。@pocket には出ない |
| 見出し | @pocket の列見出し。**完全一致で列を解決する**ので1文字も変えられない |
| 型 | 下記「型の一覧」を参照 |
| 必須 | 「必須」＝表示中は入力必須。「任意」＝未入力でも保存できる |
| 表示条件 | 空欄は常に表示。条件記号は第2章に対応 |

**保存対象の区分**が3つある。

- **通常**：画面に出て、@pocket にも保存する
- **画面のみ**：画面の入力補助専用。**@pocket には保存しない**（対応する列を持たない）
- **裏側**：画面には出さないが、保存時にサーバが値を作って書き込む

### 型の一覧

| 型 | 画面での扱い | @pocket へ送る形 |
|---|---|---|
| text | 自由入力 | 前後の空白を落とした文字列 |
| select | 単一選択 | 選んだ選択肢の文字列そのもの |
| radio | 単一選択（ラジオ） | 同上 |
| checkbox-group | 複数選択 | **選択肢見出しの配列**（文字列ではない） |
| date | 日付 | `YYYY/MM/DD`（内部は `YYYY-MM-DD` で持つ） |
| phone | 電話番号 | ハイフン区切り（例 `090-1234-5678`） |
| postal-code | 郵便番号 | `000-0000`（7桁そろったときだけ） |
| comma-integer | 画面は3桁カンマ表示 | **カンマなしの整数文字列** |
| pt-integer | 同上（PT用） | 同上 |
| decimal-kw | 小数第3位まで（四捨五入しない） | 小数点付き文字列 |

## 2. 表示条件のロジック

**判定は1つの関数に集約する**（実装名 `isCustomerInfoFormFieldVisible(key, values)`）。
表示・必須・保存の3か所が**同じ関数を呼ぶ**こと。別々に書くと必ずズレる（第6章）。

```
関数 isFieldVisible(key, values) -> boolean:
    # 比較の前に前後の空白を落とす。NFKC 正規化はしない（後述の例外を除く）
    installationType = trim(values.installationType)
    ...

    条件A  key == "referralFee"
           → introduction ∈ {(DC)工務店OBリスト, ソーラーパートナーズ, タイナビ, 工務店トスアップ}

    条件B  key == "builderOrTorachiName"
           → introduction ∈ {(DC)工務店OBリスト, 工務店トスアップ, トラーチ倶楽部, 卸案件, お客様紹介}

    条件C  key ∈ {panelCombo, panelModel1, panelCount1, panelCapacityKw}
           → installationType ∉ {蓄電池のみ, パワコン取替のみ}

    条件D  key ∈ {panelModel2, panelCount2}
           → 条件C かつ panelCombo == "有"

    条件E  key == "powerConModel2"
           → powerConCount == "2"

    条件F  key ∈ {batteryMulti, batteryCapacity1}
           → installationType ∉ {太陽光パネルのみ, パワコン取替のみ}

    条件G  key == "batteryCapacity2"
           → 条件F かつ batteryMulti == "有"

    条件H  key == "wiringMethod"
           → installationType ∈ {太陽光パネル+蓄電池, 蓄電池のみ}

    条件I  key == "ecoCuteModel"   → ecoCuteNew == "有"
    条件J  key == "ihModel"        → ihNew == "有"
    条件K  key == "v2hModel"       → v2hNew == "有"

    条件L  key == "indoorSurveyScheduledDate"
           → NFKC 正規化して trim した indoorSurveyStatus == "未実施"

    条件M  key == "roofMaterial"
           → installationType ∉ {蓄電池のみ, パワコン取替のみ}

    条件N  key == "roofMaterialModel"
           → 条件M かつ roofMaterial ∈ {平板瓦, 洋瓦, 和瓦, その他}

    条件O  key ∈ {extraPartsUrl, extraPartsName, extraPartsAmount}
           → extraParts == "有"

    条件P  key ∈ {creditCompany, loanPaper, groupCreditLifeInsurance}
           → paymentMethod ∈ {ソーラーローン, 頭金+ソーラーローン}

    条件Q1 key == "cashAmount" → paymentMethod ∈ {頭金+ソーラーローン, 現金一括}
    条件Q2 key == "loanAmount" → paymentMethod ∈ {ソーラーローン, 頭金+ソーラーローン}

    条件S1 key == "prefectureSubsidy"
           → subsidy ∈ {都道府県+市区町村, 都道府県, 都道府県+市区町村+その他, 都道府県+その他}
    条件S2 key == "citySubsidy"
           → subsidy ∈ {都道府県+市区町村, 市区町村, 都道府県+市区町村+その他, 市区町村+その他}
    条件S3 key == "otherSubsidy"
           → subsidy ∈ {その他, 都道府県+市区町村+その他, 市区町村+その他, 都道府県+その他}

    条件T  key ∈ {feedInBankAccountForm, powerOfAttorneyStorage, equipmentCertConsent,
                  operatingCostReportConsent, freeUseGenerationConsent}
           → installationType ∈ {太陽光パネル+蓄電池, 太陽光パネルのみ}

    条件U  key ∈ {powerOfAttorneyChangeCert, powerOfAttorneyIdPassword}
           → installationType ∈ {蓄電池のみ, パワコン取替のみ}

    条件V  key == "subsidyPreApplicationDocs"
           → preApplication が空でも "無" でもない

    常に非表示  key ∈ {apBranch, clBranch, batteryModel1, batteryModel2}
           → false（保存時にサーバが値を作る）

    それ以外    → true
```

補助的な判定は独立した純粋関数に切り出しておくとテストしやすい。例：

```
関数 shouldShowWiringMethod(installationType) -> boolean:
    return trim(installationType) ∈ {"太陽光パネル+蓄電池", "蓄電池のみ"}
```

## 3. 必須判定のロジック

### 3-1. 全体の免除

```
関数 isRequired(field, values, context) -> boolean:
    if field.required == false:                     return false   # 定義上つねに任意
    if context.treatAllRequiredAsOptional:          return false   # 画面都合の一括免除
    if trim(values.customerStatus) == "キャンセル":  return false   # 条件Y
    if 条件R かつ field.key ∈ {cosmeticCover, breakerAmps}: return false
    return true
```

- **条件Y（キャンセル）**：顧客ステータスが**完全一致で**「キャンセル」のとき、
  フォーム全体の必須を外す。キャンセル案件は情報が揃わないまま保存する必要があるため。
- **条件R（室内調査未実施）**：`indoorSurveyStatus` を NFKC 正規化して trim した値が
  「未実施」のとき、化粧カバーと分電盤アンペア数だけ任意にする。現地を見ないと決まらないため。

### 3-2. 未入力の判定

```
関数 isMissing(field, values, context) -> boolean:
    v = 契約金額の自動算出を反映した values          # 3-3
    if not isFieldVisible(field.key, v):  return false   # 非表示は対象外
    if not isRequired(field, v, context): return false

    # 契約金額が支払方法から自動算出される場合、利用者は入力できないので対象外
    if field.key == "contractAmount" かつ 支払方法が自動算出の対象: return false

    raw = v[field.key]
    型ごとに判定:
        checkbox-group : 区切り（, 、）で分割して1つも選ばれていなければ未入力
        comma-integer  : 数字が1つも取れなければ未入力
        pt-integer     : 同上
        postal-code    : 000-0000 形式でなければ未入力
        phone          : 電話番号として妥当な形式でなければ未入力
        decimal-kw     : 数値として読めなければ未入力
        date           : 日付として読めなければ未入力
        それ以外       : trim した結果が "" または "-" なら未入力
```

**`"-"` を未入力とみなす**のが重要。`"-"` は「非表示のときに書き込む既定値」であり、
人が入力した値ではない。

### 3-3. 契約金額の自動算出

必須判定・保存の**どちらも**この算出を通した値で行う。画面の表示と保存値を一致させるため。

```
関数 syncContractAmount(values) -> values:
    if 支払方法 == "ソーラーローン":       契約金額 = ローン金額
    if 支払方法 == "頭金+ソーラーローン":  契約金額 = 現金 + ローン金額
    if 支払方法 == "現金一括":             契約金額 = 現金
    （上記以外の支払方法では利用者の入力をそのまま使う）
```

自動算出される支払方法のとき、契約金額の入力欄は編集不可にして計算結果を表示する。

### 3-4. エラー表示

未入力の項目を集めて、見出しを並べた1行のメッセージにする。
多すぎるときは先頭8件＋「ほか N件」に丸める。

## 4. 保存時の payload 組み立て

payload は `{ 列の識別子: 値 }` の1階層のオブジェクト。**組み立ての順序に意味がある。**

### 4-1. 前処理

1. 契約金額を支払方法から引き直す（3-3）
2. 苗字・名前 → お客様名、フリガナ苗字・名前 → フリガナ を連結する
   （区切りは**全角スペース**。片方だけならそのまま）

### 4-2. 各項目のループ（中核）

```
for 各項目 in フォーム定義:
    if 項目が「画面のみ」または「裏側」: スキップ（4-3 で処理）

    visible = isFieldVisible(項目.key, values)
    raw     = trim(values[項目.key])
    hiddenFallback = 項目の非表示時既定値 ?? "-"

    # --- checkbox-group ---
    if 型 == checkbox-group:
        if visible: payload[列] = 選択肢の配列（定義に無い値は捨てる）
        else if 何も選ばれていない: payload[列] = []      # 空配列で明示的にクリア
        else: 何も入れない                                # 選択が残っているなら触らない
        continue

    # --- date ---
    if 型 == date:
        if not visible: 何も入れない; continue            # 非表示の日付は絶対に触らない
        if 日付として読める: payload[列] = "YYYY/MM/DD"
        else if 空または "-": payload[列] = ""            # 明示的なクリア
        continue

    # --- 非表示のとき ---
    if not visible:
        if shouldPreserveHidden(項目.key, raw, ...): 何も入れない; continue
        payload[列] = 非表示時の値                        # 4-4 の表
        continue

    # --- 表示中 ---
    payload[列] = 型ごとの変換結果                        # 4-4 の表
```

### 4-3. サーバ側で作る値（裏側の項目）

ループの後で次を payload に足す。**順序を守ること。**

1. **お客様名・フリガナ**：分割入力から連結した値を入れる
2. **CLPT / APPT**：PT から算出して入れる
3. **AP所属支店・CL所属支店**：
   - **担当者が変わったときだけ**名簿を引き直す（毎回引かない）
   - 引けなかったら**何も入れない**。`"-"` で潰さない
4. **AP担当者・CL担当者の送信ガード**：
   - @pocket の現在値と**同じなら payload から落とす**（無駄な更新を出さない）
   - 現在値が取れていない、または空欄になっている場合は記録を残す
   - ※ 3 の支店判定より**後**に行う。順序を逆にすると支店を引き直せなくなる
5. **蓄電池品番①②**：選択された蓄電池容量とメーカーから商品マスタを引いて入れる。
   引けなければ `"-"`
6. **更新不可の列を落とす**：@pocket 側で更新できない型（計算・ラベル・関連レコード・
   作成者・更新日時など）の列が混ざっていたら payload から除外する。
   混ざったまま送ると更新全体が 400 で落ちる

### 4-4. 値の変換規則（表示中／非表示）

| 分類 | 対象 key | 表示中・入力あり | 表示中・空 | 非表示 |
|---|---|---|---|---|
| 契約金額 | contractAmount | 自動算出後の整数（カンマなし） | `"-"` | `"-"` |
| 郵便番号 | postalCode | `000-0000` | `"-"` | `"-"` |
| 電話番号 | phone | ハイフン区切り | `"-"` | `"-"` |
| 数量・金額 | panelCount1, panelCount2, cashAmount, loanAmount, referralFee | 整数（カンマなし） | `"0"` | `"0"`（4-5 の保護が優先） |
| 容量 | panelCapacityKw | 小数（最大3桁） | `"0"` | `"0"`（同上） |
| 型番・容量 | panelModel1, panelModel2, powerConModel1, powerConModel2, batteryCapacity1, batteryCapacity2, batteryModel1, batteryModel2 | 文字列 | `"-"` | `"-"`（同上） |
| 書類16項目 | （1-8 参照） | 選んだ値 | 空文字 | `"不要"` |
| 配線方式 | wiringMethod | 選んだ値 | 空文字 | **書かない**（4-5） |
| それ以外 | | trim した文字列 | 空文字 | `"-"` |

### 4-5. 非表示になった項目の扱い（最重要）

**原則：非表示になった項目は payload から落とし、@pocket の値をそのまま残す。**

```
関数 shouldPreserveHidden(key, raw, hiddenFallback, hiddenPut) -> boolean:
    # ① 常に残す項目（選択式で "-" が選択肢に無いもの）
    if key ∈ 常時保護リスト:                          return true   # 例: wiringMethod

    # ② 数量・金額・型番は、値の有無にかかわらず残す
    if key ∈ {型番系, 数量金額系}:                     return true

    # ③ もともと空／"-" なら、既定値を書いてよい
    if raw が "" または "-":                          return false

    # ④ 既定値と同じ値なら、書いても変わらない
    if raw == hiddenFallback または raw == hiddenPut:  return false

    # ⑤ それ以外（人が入れた値が残っている）は残す
    return true
```

この保護が無かった頃、**設置種別や支払方法を切り替えた瞬間に `0` や `"-"` が
書き込まれ、切り替えを戻しても値が復元されなかった。** 再入力の負担が大きいため、
「書かない」方針に倒してある。

**選択式の列に `"-"` を書かないこと。** 選択肢に無い値が入り、画面のリストは
未選択に見えるのに値だけ入っている状態になる。新しく選択式の項目を足すときは、
①の常時保護リストに入れるか必ず確認する。

### 4-6. 表示条件が戻ったときの巻き戻し（書類16項目）

非表示のあいだに書かれた既定値「不要」は、条件が戻って再表示されたとき、
**システムが書いた分だけ**「未回収」系に戻す。人が自分で選んだ「不要」は残す。

- 追跡は編集セッション中のメモリだけで持つ（ブラウザの保存領域には置かない）
- 画面を開き直すと追跡は消えるので、**すでに保存済みの「不要」は対象外**
- 書類の表示条件は **支払方法・設置種別・事前申請有無の3つだけ**で決まる。
  それ以外の項目を変更したときは書類の値に触れないこと

### 4-7. 取込キー（自動採番列）の規約

@pocket の書き込みは「取込キー」を要求する。このアプリでは **T番号** がそれにあたる。

- **更新のとき**：レコードから現在の T番号 を読み、**payload に載せて送る**。
  新規採番はしない。読めなければ 400 で止める（読めないまま送ると別レコードが
  作られる恐れがある）
- **新規作成のとき**：自動採番の列には**空文字 `""` を載せる**。
  @pocket の仕様で、空文字を送ると採番される。**列ごと省いてはいけないし、
  値を入れてもいけない**
- 取込キーの列が @pocket 側で差し替わった直後など、既存レコードから読めない場合に
  限り「キーを載せずに送る」逃げ道を用意する。ここで例外にすると**既存レコードの
  更新がすべて落ちる**
- @pocket が 400 を返し、本文に「取込設定」「キー項目」が含まれるときは、
  「取込設定にキー項目を追加してください（自動採番のままで番号入力は不要）」という
  設定案内に読み替えて画面に出す

### 4-8. 値の最終正規化

送信の直前に、payload の各値を次のように揃える。

- `null` / 未定義 → `""`（空文字）
- 配列 → そのまま（checkbox-group 用）
- 文字列・数値・真偽値 → そのまま
- オブジェクト → 表示用の文字列に変換

## 5. @pocket との通信

### 5-1. エンドポイント

| 用途 | 操作 |
|---|---|
| 列定義の取得 | アプリのフィールド一覧を取得 |
| 検索 | お客様名でレコード一覧を取得（部分一致） |
| 1件取得 | レコードID指定で1件取得 |
| 更新 | レコードID指定で1件更新 |
| 新規 | レコード作成（このフォームからは行わない） |

アプリIDとAPIキーは**用途別**に環境変数で持つ。**値は絶対にコードや
ドキュメントに書かない。ログにも例外にも出さない。**

| 変数名 | 用途 |
|---|---|
| `ATPOCKET_DOMAIN` | 接続先ドメイン |
| `ATPOCKET_AUTH_HEADER` | 認証ヘッダ名（既定値あり） |
| `CUSTOMER_INFO_APP_ID` | お客様情報アプリのID |
| `CUSTOMER_INFO_ATPOCKET_API_KEY` および `_1` / `_2` の連番 | 読取・更新用のキー |
| `CUSTOMER_INFO_CUSTOMER_NAME_FIELD_ID` | お客様名の列（検索・表示用） |
| `CUSTOMER_INFO_CONSTRUCTION_UNIQUE_KEY_FIELD_ID` | 取込キー（T番号）の列 |
| `CUSTOMER_INFO_IMPORT_KEY_SOURCE_FIELD_IDS` | T番号が別名で返るときの読み取り元（任意） |
| `CUSTOMER_INFO_FIELD_<KEYの大文字スネーク>` | 個別の列を明示指定する上書き（任意） |

読取キーと更新キーは分けられるようにしておく。読取を複数キーで冗長化しておくと、
レート制限（429）のときに切り替えて凌げる。

### 5-2. 列（フィールド識別子）の解決

**優先順位は次のとおり。**

1. **環境変数の明示指定**：`CUSTOMER_INFO_FIELD_<KEY>` があればそれを使う
   （例：key が `installationType` なら `CUSTOMER_INFO_FIELD_INSTALLATION_TYPE`）
2. **見出しの完全一致**：フォーム定義の「見出し」とアプリ列定義の見出しを、
   NFKC 正規化・trim・小文字化して比較する
3. 見つからなければ、その項目を「解決できなかった見出し」として画面に伝える
   （その項目だけ保存対象から外れる。フォーム全体は動く）

**注意点**

- **同じ列を2つの項目に割り当てない。** 解決済みの識別子を記録しながら進め、
  すでに使われている列は次の項目に割り当てない
- **見出しが似た列の取り違えを防ぐ。** 「郵便番号」と「都道府県補助金」、
  「都道府県」と「都道府県+市区町村」のように、部分一致だと誤解決する組がある。
  項目ごとに「この語を含む見出しは除外する」規則を持たせる
- **更新できない型の列を弾く。** 計算列・ラベル・関連レコード・作成者・更新日時などは
  読み取れても書き込めない。解決の時点で除外する
- 1項目も解決できなかった場合は設定エラーとして止める（誤った列に書き込むより安全）

### 5-3. 値の読み取り

レコードの値は、正式な識別子以外（連番の別名など）で返ることがある。
複数の別名を順に見て、最初に取れた値を使う。値がオブジェクトで返る型（選択・
ユーザー選択など）は `value` / `label` / `name` / `displayValue` / `text` の順に見る。

checkbox-group は配列で返るので、画面ではカンマ区切りの文字列に直す。

### 5-4. エラー時の扱い

| 状況 | 応答 | 画面 |
|---|---|---|
| 認証なし・期限切れ | 401 | ログインし直す導線を出す |
| アプリ未設定 | 503 | 「設定されていません」の固定文言 |
| レコードが無い | 404 | 「見つかりません」 |
| 必須未入力 | 400 | 未入力項目の見出しを並べる |
| 取込キーが読めない | 400 | 設定を確認する案内 |
| @pocket のレート制限 | 429 | 「1〜2分待ってから」 |
| @pocket のその他エラー | 502 | **固定文言＋相関ID**のみ |

**エラー応答に @pocket の内部情報を出さない。** アプリID・環境変数名・APIキー・
検索した値は返さない。生のメッセージはサーバのログにだけ残し、画面には相関IDを
返して照合できるようにする。

### 5-5. 検索の制限

- 2文字未満の検索語は受け付けない（全件走査を誘発するため）
- 64文字を超える検索語も受け付けない
- 同一利用者あたり「10秒に5回」程度の頻度制限をかける
- **検索条件は「フィールド式」で組み立てる。値をそのまま渡さない**（6-5）

## 6. 落とし穴（過去の事故の記録）

実装コメントに残っている注意点。**同じ失敗を繰り返さないために、再実装でも引き継ぐこと。**

### 6-1. 表示条件と保存条件を別々に書かない

> 表示を消しただけで、画面に出ていない値が保存時に書き込まれていた。

表示・必須・保存の3か所は**同じ関数の結果**から導く。条件を書き写すと、片方だけ
直したときに「画面に無い項目が保存される」状態が生まれる。

### 6-2. 選択肢を実物と1文字でも変えない

> 書類16項目に2択の定義を当てていたが、実物は3択だった。非表示時に書き込む「不要」が
> 自分の選択肢に無く、**ラジオは未選択に見えるのに値だけ入っていた。**

選択肢は @pocket の実物をそのまま写す。並び順も変えない。
コードが参照する値（既定値・キャンセル値など）が選択肢に含まれることを
テストで固定しておくとよい。

### 6-3. 非表示になった項目を `0` や `"-"` で潰さない

> 設置種別や支払方法を切り替えると数量・金額・型番が一時的に非表示になり、
> **その時点で書き込まれて値が失われていた。表示条件を戻しても復元されない。**

非表示になった項目は payload から落とす（4-5）。

### 6-4. システムが書いた既定値と、人が選んだ値を区別する

> 非表示のあいだに書かれた「不要」が条件を戻しても残り、
> **回収していないのに「書類は揃っている」と見なされていた。**

システムが書いた分だけを巻き戻す（4-6）。人の選択は消さない。

### 6-5. 検索条件に値をそのまま渡さない

> 一覧取得の検索条件に値そのものを渡していたところ、絞り込みとして解釈されず
> **毎回全件が返っていた。** 1回の照合で数千件を運び、上限を超えると「見つからない」を
> 返すようになる。その結果、**同じ顧客のレコードが二重に作られた。**

`列 = "値"` の形（フィールド式）で組み立て、値はエスケープする。
絞り込みが効かなかったとき（例外が出た／1ページが満杯で返った）は全件走査に落とし、
**黙って「見つからない」を返さない**。落ちたことは警告として記録する。

### 6-6. 担当者の所属支店を毎回引き直さない

> 保存のたびに名簿を引き直し、引けなければ `"-"` で潰していた。

担当者が変わったときだけ引き直し、**引けなければ書かない**。

### 6-7. 更新不可の列を payload に混ぜない

計算列・関連レコード・作成者などを含めると、**更新全体が 400 で落ちる**。
列の解決時と送信直前の2か所で除外する。

### 6-8. 契約金額は画面と保存で同じ計算を通す

編集不可の表示値と保存値がずれると、画面で見た金額と @pocket の値が食い違う。
必須判定・payload 組み立ての両方で同じ算出関数を通す（3-3）。

### 6-9. 見出しが似た列の取り違え

「郵便番号」と「都道府県補助金」、「都道府県」と「都道府県+市区町村」など。
完全一致で解決し、それでも紛れる項目には除外語の規則を持たせる（5-2）。

### 6-10. 自動採番の列は空文字で送る

省略すると採番されない。値を入れてもいけない。**空文字 `""` を載せる**のが規約（4-7）。

### 6-11. 保存後にキャッシュを捨てる

レコード一覧や「キーからレコードIDを引く」仕組みにキャッシュを持つ場合、
**保存のたびに捨てる**。捨て忘れると、保存した案件が「未入力一覧」に残り続けたり、
連携が既存レコードを見つけられずに二重作成したりする。

### 6-12. 保存の副作用は本体を止めない

監査ログ・外部ストレージのフォルダ名追随・通知などは、失敗しても保存を成功のまま
にする。逆に、**保存より先に副作用を実行しない**（保存に失敗したのに通知だけ飛ぶ
状態を作らない）。

### 6-13. 既存レコードに初期値を書き込まない

新規登録時の既定値を、既存レコードを開いたときにも適用してはいけない。
**利用者が触っていない項目が、別項目を直して保存しただけで書き換わる。**
値が無い既存レコードは空のまま開き、表示中なら必須で入力させる。

## 7. 実行時に取得する選択肢

第1章で「実行時に取得」と書いた7項目は、フォーム定義に選択肢を持たない。
画面を開いたときに @pocket の別アプリから読み、選択肢を組み立てる。

**比較はすべて完全一致**（NFKC 正規化と前後空白の除去のみ）。
以下に書いた値は @pocket の実物をそのまま引き写したもので、**1文字でも違うと
候補が0件になる**。値を変えるときは @pocket 側と同時に変えること。

### 7-1. メーカー

| | |
|---|---|
| **取得元** | `TRADING_PARTNER_APP_ID`（取引先会社一覧） |
| **読み取る列** | `TRADING_PARTNER_COMPANY_TYPE_FIELD_ID`（未設定時は見出し「会社種別」）<br>`TRADING_PARTNER_TRADE_STATUS_FIELD_ID`（同「取引状況」）<br>`TRADING_PARTNER_COMPANY_NAME_FIELD_ID`（同「取引会社名」） |
| **絞り込み** | 会社種別が **`メーカー`** かつ 取引状況が **`取引中`** |
| **並び順** | コード側で日本語ロケールの昇順に並べ替える（@pocket の順序は使わない）。重複は除去 |
| **依存** | なし |
| **現在値** | 候補に無ければ**末尾に足してから再ソート**する |

（実装では `enrichCustomerInfoFormFieldsWithManufacturers`）。再実装では
専用の口を用意してよい。

### 7-8. 応答の形

**`options` はすべて文字列の配列**で、オブジェクトの配列ではない。

```jsonc
// 信販会社 / 施工業者
{ "options": ["…"], "configured": true }
{ "options": [], "configured": false, "error": "…" }   // 失敗時のみ error

// パネル品番 / パワコン品番 / 蓄電池容量
{ "options": ["…"], "configured": true }
{ "options": [], "configured": false }                  // メーカー未選択・アプリ未設定
{ "error": "…" }                                        // 取得失敗

// AP/CL担当者
{
  "configured": true,
  "configError": "…",        // 任意
  "rosterEmpty": true,       // 任意
  "ap": { "options": ["…"], "defaultName": "…" },   // defaultName は null あり
  "cl": { "options": ["…"], "defaultName": "…" }
}

// メーカー（レコード取得の応答に混ざる）
{
  "recordId": "…",
  "formFields": [
    {
      "key": "manufacturer",
      "fieldId": "…",
      "label": "…",
      "type": "select",
      "options": ["…"],
      "optionsPending": false,
      "value": "…"
    }
  ]
}
```

`configured: false` は「アプリが設定されていない」、`options: []` は「候補が0件」を
表す。**画面はこの2つを区別していない**（7-9 の④を参照）。

### 7-9. 注意点（現状の作りと、再実装での扱い）

#### ① @pocket 側では絞り込んでいない

取引先会社一覧・商品一覧とも、**全件を取得してからコード側でフィルタ**している。
検索条件を @pocket へ渡していないため、**レコードが増えるとページングの回数が増える**
（1ページ1000件）。

#### ② 同じアプリを3回ずつ全件取得している

- 取引先会社一覧 … メーカー／信販会社／施工店 で **3回**
- 商品一覧 … パネル／パワコン／蓄電池 で **3回**

いずれも会社種別・商品種別が違うだけで、読む列も条件の骨格も同じ。
**1回取ってから種別で振り分ければ 6回が 2回になる**が、現状はキャッシュも
取得もそれぞれ独立している。

**社内システムで実装する際は、この形を踏襲する必要はない。**

#### ③ 現在値が候補に無ければ末尾に足して再ソートする

@pocket に入っている値が、取引状況の変更や商品の廃番で候補から外れることがある。
そのまま候補だけを出すと、**画面上でその値が消え、保存時に失われる**。
メーカー・品番・容量・施工業者は、候補に無い現在値を足してから並べ替えている。

（信販会社と AP/CL担当者は足していない。前者は候補が空なら入力欄自体が
テキストに変わるため、後者は名簿にある担当者だけを選ばせる方針のため。）

#### ④ 空・エラー・未設定の見分けが画面では付かない

信販会社・施工業者は、**アプリ未設定・取得失敗・候補0件のどれでも**同じく
テキスト入力へフォールバックする。利用者からは「選べない」としか見えず、
原因の切り分けはサーバのログに頼ることになる。

**社内システムでは、この3つを区別して表示することを勧める**
（「設定されていません」「一時的に取得できません」「候補がありません」）。

#### ⑤ 1画面あたりの呼び出し回数とキャッシュ

1件のレコードを開くまでに、@pocket への問い合わせは
**キャッシュが冷えていれば10回超、温まっていれば2〜3回**発生する。
温まっていても残るのは、お客様情報アプリへの列定義取得・レコード取得・検索で、
**これらはキャッシュしていない**。

@pocket の利用制限は **サイト単位で100秒あたり100回**（API キー単位ではない）。
**既存の LIFF アプリと社内システムはこの枠を共有する**ため、
社内システム側にもキャッシュが要る。

現在の TTL は次のとおり。

| 対象 | TTL |
|---|---|
| 選択肢（取引先会社一覧・商品一覧） | 10分（取得失敗時は1分） |
| スタッフ名簿・AP/CL候補 | 30分 |

いずれもプロセスのメモリに置いているだけなので、実行環境が分かれると共有されない。
同じ内容の取得が同時に走ったときは1本にまとめている（後発は先行の結果を待つ）。
